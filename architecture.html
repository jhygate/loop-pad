Loop Pad Internals

Nine pads, one metronome, one browser. This page maps how a press becomes a loop that can never drift: the modules and their conversations, the state machine and who fires each event, the roll-through capture pipeline, the shared grid, and the sound-trigger gate.

1The cast

Each Pad is an orchestrator that owns five collaborators and does almost no work itself. Decisions live in the planner, rules in the state machine, sound in the audio handler, pixels in the view. Arrows below are the actual method calls; dashed arrows are events flowing back.

2One press, one journey

Every event — a finger, a timer, the audio engine, the gate — funnels through Pad.transitionState(event), which always runs the same pipeline:

  1. Plan. planner.planFor(state, event) returns a SyncPlan: a decision (immediate or wait) paired with the side effect that follows from it.
  2. Transition. The state machine picks the next state from its rule table, reading only the plan's decision and the settings.
  3. Propagate looping. audioHandler.setLooping() pushes the (possibly toggled) loop flag onto any live source.
  4. Apply the plan. The plan's apply() fires: open a capture window, schedule a boundary timer, schedule playback at an exact time.
  5. Act on the state. handleStateChange(state) maps state to sound: start the recorder, stop it, start/stop the gate, play, delete.
  6. Persist & render. Finished takes mirror to IndexedDB, changed flags to localStorage; the view mutates only what changed.

The load-bearing idea: decisions are made once, up front, from timestamps — then the audio work happens either at an exact scheduled time (playback) or once at the end (slicing). Nothing timing-critical rides on a JavaScript callback.

4Recording: roll through, cut once

The recorder starts the moment you press and never waits. All alignment happens once, at the end, as a slice of the decoded audio. Timers and detection only choose where to cut — their jitter can change what gets discarded, never the result. Shown here: a sound-triggered, synced take.

5The grid: sync by construction

There is no drift correction anywhere, because two invariants make drift impossible to express. Every synced buffer's length is an exact integer multiple of the cycle it locked to, and every synced playback claims a start time exactly on a boundary — then native looping (loop = true) repeats it sample-perfectly on the audio thread, with no JavaScript in the loop.

6The gate: sound as a virtual press

The InputGate is a sensor, not a decision-maker. Every ~15 ms it measures the input's RMS; while armed it builds a noise-floor estimate from the quiet, and the first frames to clear floor × trigger margin become a timestamped onset — which then flows through the planner exactly as a press would. Detection only needs to be roughly right: synced takes are cut on the grid, unsynced takes are refined by walking back through the decoded samples to the attack's true edge.

Known open issue. An onset currently always claims the boundary behind it — so entering a smidge before a bar line claims the previous bar and manufactures nearly a bar of silence. The agreed fix: run onsets through the same snap-back slider as presses, and make the onset wrap variable-length so a forward claim can never lose audio.
